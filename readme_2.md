# Как работает run.py

`run.py` автоматизирует проверку модели: подготавливает файлы, вызывает SPIN и GCC, запускает проверки по очереди и собирает результаты в отчёт. Модель описана в `modbus.pml`, а проверяемые LTL-свойства — в `properties.pml`.

В этом документе разобран текущий Python-скрипт после разделения на функции. Объяснение идёт по порядку выполнения программы.

## 1. Как запустить

Откройте PowerShell в папке проекта и выполните:

```powershell
python .\run.py
```

Нужны Python 3.9 или новее, SPIN и GCC. Все используемые Python-модули входят в стандартную библиотеку, устанавливать дополнительные пакеты не требуется. Текущие команды рассчитаны на Windows.

В `config.json` находятся пути к двум программам:

```json
{
  "spin": "%LOCALAPPDATA%/Programs/Spin/spin.exe",
  "cc": "C:/msys64/ucrt64/bin/gcc.exe"
}
```

`spin` — путь к SPIN. `cc` — путь к компилятору C; в этом проекте используется GCC. При другом расположении программ поменяйте эти значения. Аргументы при запуске скрипта передавать не нужно.

Скрипт сам создаст папку вида `verification_results/run_d96kiwls/`. Для каждого запуска имя будет новым. В консоли появятся команды и результаты отдельных проверок, например:

```text
Проверка 2/14: p01_crc_ignored
[PASS] p01_crc_ignored: состояний 10914592, глубина 115711, ошибок 0
```

В конце выводятся общий итог и расположение `report.txt`.

## 2. Какие части есть в скрипте

| Функция | Задача |
| --- | --- |
| `main()` | Организует весь запуск. |
| `prepare_files()` | Копирует входные файлы, читает настройки и находит имена свойств. |
| `build_verifiers()` | Вызывает SPIN и компилирует две программы проверки. |
| `run()` | Запускает одну внешнюю команду и записывает её вывод в лог. |
| `run_checks()` | По очереди выполняет проверки и формирует общий отчёт. |
| `verify()` | Выполняет одну проверку и возвращает её статус с пояснением. |
| `check_search_output()` | Проверяет настройки и результат поиска по тексту отчёта верификатора. |
| `save_counterexample()` | Сохраняет найденную ошибочную последовательность действий и её пошаговый разбор. |

### Импорты

В начале файла перечислены используемые модули:

| Импорт | Зачем нужен в этом скрипте |
| --- | --- |
| `json` | Прочитать `config.json` и получить словарь настроек. |
| `os` | Подставить значения переменных среды в пути и дополнить `PATH`. |
| `Path` из `pathlib` | Работать с путями к файлам и папкам. |
| `re` | Найти имена LTL-свойств и числа в отчётах с помощью регулярных выражений. |
| `shutil` | Скопировать входные файлы в папку запуска. |
| `subprocess` | Запустить SPIN, GCC и собранные программы. |
| `sys` | Настроить кодировку вывода и передать системе код завершения скрипта. |
| `tempfile` | Создать папку с уникальным именем для очередного запуска. |

### Папка проекта — ROOT

```python
ROOT = Path(__file__).resolve().parent
```

`__file__` — имя файла самого скрипта. `Path(...)` представляет его как путь, `resolve()` получает абсолютный путь, а `parent` выбирает родительскую папку. В результате `ROOT` указывает на каталог, где лежит `run.py`.

Выражение `ROOT / "config.json"` означает «файл `config.json` внутри папки `ROOT`». Оператор `/` для объектов `Path` соединяет части пути.

Благодаря `ROOT` скрипт ищет модель и настройки рядом с собой, даже если его запускают из другой рабочей папки.

### Как читать заголовки функций

Например:

```python
def check_search_output(name: str, output: str) -> int:
```

`def` объявляет функцию. В скобках находятся её параметры: `name` и `output`. Подсказка `str` означает строку, а `-> int` — что функция возвращает целое число.

В других заголовках встречаются:

| Запись | Значение |
| --- | --- |
| `Path` | Путь к файлу или папке. |
| `list[str]` | Список строк, например имён свойств. |
| `tuple[str, str]` | Пара из двух строк: статус и пояснение. |
| `tuple[Path, Path, list[str]]` | Три значения: путь к SPIN, путь к GCC и список свойств. |
| `None` | Функция выполняет действия и не возвращает полезного результата. |

Это подсказки для читателя и редактора. Python автоматически не проверяет по ним типы переданных значений. Строки в тройных кавычках под заголовками функций кратко описывают их назначение.

## 3. Точка входа и main()

Хотя `main()` находится ближе к концу файла, именно с неё начинается основная работа:

```python
if __name__ == "__main__":
    sys.exit(main())
```

При выполнении `python run.py` условие истинно, вызывается `main()`. Когда она вернёт число, `sys.exit(...)` передаст его операционной системе как код завершения. При импорте файла из другого Python-скрипта этот блок не выполняется.

Объявления функций выше по файлу сами по себе не запускают проверки: они описывают действия, которые выполнятся при вызове.

### Подготовка папки

В начале `main()`:

```python
sys.stdout.reconfigure(encoding="utf-8")
results = ROOT / "verification_results"
results.mkdir(exist_ok=True)
folder = Path(tempfile.mkdtemp(prefix="run_", dir=results))
```

- `sys.stdout.reconfigure(...)` задаёт UTF-8 для вывода скрипта в консоль.
- `results` — общий каталог всех запусков.
- `mkdir(exist_ok=True)` создаёт его; наличие уже существующей папки допустимо.
- `folder` — отдельная папка текущего запуска.
- `prefix="run_"` задаёт начало её имени, `dir=results` — место создания.

`mkdtemp()` добавляет уникальную часть имени. Созданная таким способом папка остаётся после завершения программы, поэтому логи доступны для изучения. Это поведение описано в [документации Python о mkdtemp](https://docs.python.org/3/library/tempfile.html#tempfile.mkdtemp).

### Общий порядок действий

Главные вызовы в `main()`:

```python
spin, cc, properties = prepare_files(folder)
build_verifiers(folder, spin, cc)
```

Первая функция возвращает три значения, которые сразу записываются в переменные `spin`, `cc` и `properties`. Это называется распаковкой. Вторая функция собирает программы проверки.

Оба вызова находятся внутри `try`. Если подготовка не удалась, блок `except` получает исключение в переменную `error`. Например, причиной может быть отсутствующий файл, неправильный JSON, отсутствие нужного ключа настройки или ошибка внешней команды.

В таком случае `message` содержит описание проблемы. Скрипт печатает его, записывает в `report.txt` и возвращает `2`. Проверки после неудачной подготовки не запускаются.

При успешной подготовке выполняется:

```python
return run_checks(folder, spin, properties)
```

Результат `run_checks()` становится результатом `main()`.

## 4. prepare_files(): исходники, настройки и список свойств

Функция получает `folder` — папку текущего запуска.

Сначала цикл копирует туда `modbus.pml`, `properties.pml` и `config.json`:

```python
for filename in ("modbus.pml", "properties.pml", "config.json"):
    shutil.copy2(ROOT / filename, folder / filename)
```

`filename` по очереди принимает каждое из трёх имён. Оригиналы остаются в проекте. Далее программы работают с копиями: так вместе с результатами сохраняются использованные входные данные.

Затем читается конфигурация:

```python
config = json.loads((folder / "config.json").read_text(encoding="utf-8"))
spin = Path(os.path.expandvars(config["spin"]))
cc = Path(os.path.expandvars(config["cc"]))
```

`read_text()` получает содержимое файла как строку. `json.loads()` превращает её в словарь `config`. Выражение `config["spin"]` берёт значение по ключу `spin`.

`os.path.expandvars()` подставляет переменные среды. Например, `%LOCALAPPDATA%` в пути к SPIN заменяется каталогом локальных данных текущего пользователя. После этого `spin` и `cc` содержат пути к программам.

Следующая строка добавляет каталог GCC в начало `PATH`:

```python
os.environ["PATH"] = str(cc.parent) + os.pathsep + os.environ.get("PATH", "")
```

`cc.parent` — папка компилятора, `str(...)` превращает путь в строку. `os.pathsep` — разделитель каталогов в `PATH`, на Windows это `;`. `get("PATH", "")` читает прежнее значение или возвращает пустую строку, если его нет.

Это помогает находить GCC и необходимые ему DLL при вызове дочерних программ. Изменение действует в процессе скрипта и его дочерних процессах; системные настройки Windows не редактируются.

### Поиск имён LTL-свойств

`source` содержит текст скопированного `properties.pml`. Имена извлекаются так:

```python
properties = re.findall(r"^ltl\s+(\w+)\s*\{", source, re.MULTILINE)
```

Регулярное выражение — шаблон для поиска текста. Здесь его части означают:

| Часть | Что ищется |
| --- | --- |
| `^ltl` | Слово `ltl` в начале строки. |
| `\s+` | Один или несколько пробельных символов. |
| `(\w+)` | Имя свойства; скобки выделяют то, что нужно вернуть. |
| `\s*` | Возможные пробелы после имени. |
| `\{` | Открывающая фигурная скобка. |
| `re.MULTILINE` | Позволяет `^` обозначать начало каждой строки файла. |

Буква `r` перед строкой сохраняет обратные слеши для регулярного выражения.

Например, из `ltl p01_crc_ignored {` получается `p01_crc_ignored`. Таким образом создаётся список `properties`. Объявления в файле нужно оформлять в принятом формате: `ltl` начинается с начала строки.

Если список пуст, функция вызывает `raise RuntimeError(...)`: без найденных свойств продолжать проверку бессмысленно. В обычном случае возвращаются `spin`, `cc`, `properties`.

## 5. build_verifiers(): создание программ проверки

Параметры функции — `folder`, `spin`, `cc`. Она вызывает внешние программы через вспомогательную функцию `run()`.

Сначала выполняются `spin -V` и `gcc --version`. Версии сохраняются в логах; версия SPIN также печатается в консоль.

Затем выполняется команда:

```text
spin -a properties.pml
```

SPIN создаёт C-код верификатора, в том числе `pan.c`. Файл `properties.pml` подключает модель, поэтому сгенерированный код учитывает и поведение модели, и её свойства. Назначение `spin -a` описано в [руководстве SPIN](https://spinroot.com/spin/Man/Spin.html).

GCC компилирует этот код два раза:

```text
gcc -O2 -DCOLLAPSE -DSAFETY -DNOCLAIM -o pan_safety.exe pan.c
gcc -O2 -DCOLLAPSE -o pan_ltl.exe pan.c
```

| Параметр | Назначение |
| --- | --- |
| `-O2` | Включает оптимизацию компилятора. |
| `-DCOLLAPSE` | Включает сжатие хранимых состояний. |
| `-DSAFETY` | Отключает поиск циклов. |
| `-DNOCLAIM` | Исключает наблюдатель LTL, называемый never claim. |
| `-o имя.exe` | Задаёт имя собранной программы. |
| `pan.c` | Исходный C-файл для компиляции. |

Директивы верификатора приведены в [руководстве Pan](https://spinroot.com/spin/Man/Pan.html).

Получаются две программы: `pan_safety.exe` проверяет конечные состояния без LTL, а `pan_ltl.exe` проверяет LTL-свойства. Такое разделение нужно, потому что при включённом never claim встроенная проверка недопустимых конечных состояний отключается.

`build_verifiers()` ничего не возвращает. Результат её работы — файлы программ в `folder`.

## 6. run(): выполнение одной команды

Этой функцией пользуются и сборка, и сами проверки, и разбор контрпримера.

| Параметр | Что содержит |
| --- | --- |
| `command` | Список: путь к программе, затем её аргументы. |
| `folder` | Папку, в которой выполняется команда. |
| `log_name` | Имя файла для сохранения вывода. |

Например, `[str(spin), "-a", "properties.pml"]` — список из трёх строк. Программа получает аргументы отдельно, поэтому путь с пробелами не приходится вручную заключать в кавычки.

`command_text = subprocess.list2cmdline(command)` создаёт строку для показа команды и записи в лог. Выполняется исходный список `command`.

```python
result = subprocess.run(
    command, cwd=folder, stdout=subprocess.PIPE, stderr=subprocess.STDOUT,
    text=True, encoding="utf-8", errors="replace", timeout=180,
)
```

Параметры вызова описаны в [документации subprocess.run](https://docs.python.org/3/library/subprocess.html#subprocess.run):

| Параметр | Действие |
| --- | --- |
| `cwd=folder` | Задаёт рабочую папку внешней программы. |
| `stdout=subprocess.PIPE` | Собирает обычный вывод. |
| `stderr=subprocess.STDOUT` | Добавляет сообщения об ошибках в тот же вывод. |
| `text=True`, `encoding="utf-8"` | Возвращает вывод как текст UTF-8. |
| `errors="replace"` | Заменяет недекодируемые символы. |
| `timeout=180` | Ограничивает ожидание одной команды 180 секундами. |

`result` содержит итог запуска. `result.stdout` — собранный текст, `result.returncode` — код завершения внешней программы. При ненулевом коде `run()` вызывает `RuntimeError`, при нулевом возвращает `result.stdout`.

`log_path = folder / log_name` задаёт путь к логу. Команда и её полный вывод записываются туда через `write_text()`.

Команда показывается в консоли перед запуском. Её внутренний вывод накапливается до завершения; построчная трансляция в консоль не выполняется. `flush=True` в `print()` позволяет сразу показать саму команду.

### Ошибки запуска

`try` содержит запуск программы. Два блока `except` обрабатывают проблемы:

- `subprocess.TimeoutExpired`: команда не завершилась вовремя. В переменную `output` берётся частичный вывод из `error.stdout`; при его отсутствии используется `b""`, пустая последовательность байтов. Если это байты, `decode()` переводит их в текст. В лог добавляется `TIMEOUT`.
- `OSError`: программу не удалось запустить, например из-за неверного пути. В лог записывается причина.

После записи лога оба случая вызывают `RuntimeError`. Запись `raise ... from error` сохраняет связь с исходным исключением. Особенности частичного вывода при тайм-ауте приведены в [описании TimeoutExpired](https://docs.python.org/3/library/subprocess.html#subprocess.TimeoutExpired).

## 7. run_checks(): очередь проверок и общий отчёт

Функция получает `folder`, `spin` и список `properties`.

### Список команд

В `checks` каждый элемент — пара: имя проверки и список аргументов команды. Первым добавляется `structure`:

```text
pan_safety.exe -m1000000 -w22 -q -b
```

Затем цикл по `properties` добавляет отдельную команду для каждого свойства. Например:

```text
pan_ltl.exe -a -N p01_crc_ignored -m1000000 -w22 -b
```

Значения параметров приведены в [руководстве Pan](https://spinroot.com/spin/Man/Pan.html):

| Параметр | Назначение |
| --- | --- |
| `-a` | Искать принимающие циклы. |
| `-N имя` | Выбрать LTL-свойство по имени. |
| `-m1000000` | Ограничить глубину поиска миллионом шагов. |
| `-w22` | Задать начальный размер хеш-таблицы: `2^22` ячеек. |
| `-q` | Требовать пустые каналы в допустимых конечных состояниях. |
| `-b` | Считать превышение глубины ошибкой. |

`spin -a` создаёт C-код, а `pan_ltl.exe -a` включает поиск циклов: значение параметра зависит от программы.

Предел глубины относится к обходу графа состояний. Он не задаёт максимальное число посылок в модели. При его достижении скрипт выдаст `ERROR`.

Проверка `structure` ищет недопустимые конечные состояния, в том числе блокировки. Условие `-q` относится к окончанию работы модели. В текущем бесконечном обмене пустоту каналов после каждой транзакции проверяет свойство `p14_completion_clean`.

### Выполнение и накопление результатов

`counts` — словарь счётчиков:

```python
counts = {"PASS": 0, "FAIL": 0, "ERROR": 0}
```

`lines` — список строк будущего отчёта. Цикл выполняет проверки последовательно:

```python
for number, (name, command) in enumerate(checks, start=1):
```

`enumerate()` добавляет порядковый номер `number`, начиная с единицы. Каждая пара из `checks` распаковывается в `name` и `command`.

Вызов `verify(...)` возвращает две строки — `status` и `detail`. По статусу увеличивается счётчик: `counts[status] += 1`. Строка `line` содержит статус, имя и подробности. Она добавляется в `lines` и сразу печатается.

После завершения цикла формируется строка `summary` с общими числами. Выражение `"\n".join(lines)` соединяет строки отчёта переводами строк. Полученный текст записывается в `report.txt`.

Код завершения выбирается так:

| Код | Условие |
| --- | --- |
| `0` | Все проверки получили `PASS`. |
| `1` | Есть `FAIL`, но нет `ERROR`. |
| `2` | Есть хотя бы один `ERROR`. |

Если одна проверка получила `FAIL` или `ERROR`, цикл переходит к следующей: итоговый отчёт показывает результаты всей очереди.

## 8. verify(): результат одной проверки

Параметры — имя `name`, команда `command`, папка `folder` и путь к `spin`.

Сначала `run()` выполняет команду и сохраняет её вывод в `output`. Имя лога получается из имени проверки: например, `p01_crc_ignored.log`.

Затем:

```python
error_count = check_search_output(name, output)
```

`error_count` — число нарушений из отчёта верификатора. Далее возможны три исхода.

### FAIL: нарушение найдено

При `error_count > 0` вызывается `save_counterexample()`. Если сохранение и разбор удались, функция возвращает:

```python
("FAIL", "Найден контрпример: p01_crc_ignored_trace.log")
```

Контрпример — конкретная последовательность действий модели, нарушающая проверяемое требование. Для вывода `FAIL` достаточно одной такой последовательности, завершать обход всего графа не требуется.

### PASS: завершённый поиск без нарушений

При нуле нарушений дополнительно проверяется отсутствие сообщения `search not completed`. Из отчёта извлекаются:

- `states` — результат поиска числа сохранённых состояний шаблоном `r"([\d.e+]+) states, stored"`;
- `depth` — результат поиска достигнутой глубины шаблоном `r"depth reached (\d+)"`.

Обе переменные содержат результаты `re.search()`. Вызов `.group(1)` берёт текст из первой группы в круглых скобках. Если статистика не найдена, выдавать `PASS` скрипт не будет.

Например, результат функции:

```python
("PASS", "состояний 10914592, глубина 115711, ошибок 0")
```

Число состояний показывает объём исследованного графа, а глубина — достигнутую глубину поиска. Эти числа не обозначают количество отправленных запросов.

### ERROR: проверку не удалось надёжно выполнить

Исключения `OSError` и `RuntimeError` перехватываются в `except`. Переменная `error` содержит причину, которая попадает в пояснение результата `ERROR`.

| Статус | Как его понимать |
| --- | --- |
| `PASS` | Завершённый поиск не обнаружил нарушения проверяемого требования. |
| `FAIL` | Найден и разобран контрпример. |
| `ERROR` | Не удалось получить надёжный результат: например, не хватило ресурсов, не запустилась программа или не сохранился контрпример. |

Нулевой код завершения внешней программы сам по себе не означает `PASS`: решение принимается после разбора её отчёта.

## 9. check_search_output(): проверка отчёта верификатора

Функция принимает `name` и `output`, возвращает количество нарушений. При непригодном результате вызывает исключение.

Первый шаблон ищет поле вида `errors: 0`:

```python
errors = re.search(r"\berrors:\s*(\d+)", output)
```

Здесь `\b` — граница слова, `\s*` — возможные пробелы, `\d+` — одна или несколько цифр. Переменная `errors` содержит найденное совпадение или `None`. В конце `int(errors.group(1))` переводит найденные цифры в целое число.

Кортеж `limits` содержит сообщения о нехватке глубины, памяти или других ресурсов:

```python
limits = (
    "max search depth too small", "depth limit reached", "out of memory",
    "cannot allocate", "vectorsz is too small", "time limit reached",
)
```

Условие `any(text in output.lower() for text in limits)` проверяет, встретилось ли хотя бы одно из них. `text` по очереди принимает элементы `limits`, а `lower()` приводит отчёт к нижнему регистру. Наличие такого сообщения или отсутствие поля `errors` вызывает исключение.

Далее проверяется строка `Full statespace search for:`. Она обозначает режим полного поиска; сама по себе эта строка ещё не подтверждает завершение поиска — это отдельно проверяет `verify()`.

Наконец проверяются включённые режимы:

| Проверка | Что требуется в выводе |
| --- | --- |
| `structure` | `invalid end states +`: проверка недопустимых конечных состояний включена. |
| LTL-свойство | `never claim +` и `acceptance cycles +`: наблюдатель LTL и поиск принимающих циклов включены. |

Плюс ищется как `\+`, потому что в регулярном выражении обычный `+` имеет специальное значение. Это защищает от ситуации, когда программа запущена в неподходящем режиме и поэтому не проверяет нужное требование.

## 10. save_counterexample(): сохранение и разбор ошибки

Параметры — имя проверки `name`, папка `folder` и путь к `spin`.

По умолчанию верификатор этой модели сохраняет ошибочную последовательность в `properties.pml.trail`. Переменная `trail` содержит путь к этому файлу.

Если файла нет, вызывается исключение: заявленное нарушение нельзя разобрать. Если файл есть, он переименовывается:

```python
saved_trail = folder / (name + ".trail")
trail.rename(saved_trail)
```

Для `p01_crc_ignored` получится `p01_crc_ignored.trail`. Так разные проверки получают отдельные файлы контрпримеров. `saved_trail` содержит новый путь, а `saved_trail.name` — только имя файла без папки.

Для пошагового воспроизведения выполняется:

```text
spin -t -p -g -l -k p01_crc_ignored.trail properties.pml
```

Параметры воспроизведения описаны в [руководстве SPIN](https://spinroot.com/spin/Man/Spin.html):

| Параметр | Назначение |
| --- | --- |
| `-t` | Воспроизвести последовательность из контрпримера. |
| `-p` | Показывать выполняемые операторы и процессы. |
| `-g` | Показывать значения глобальных переменных. |
| `-l` | Вместе с `-p` показывать локальные переменные. |
| `-k имя.trail` | Выбрать файл контрпримера. |

Вызов `run()` записывает вывод в `p01_crc_ignored_trace.log`. Его можно читать как протокол ошибочного выполнения: какие действия происходили и как менялись переменные. Функция `save_counterexample()` ничего не возвращает; её результат — сохранённые файлы.

## 11. Какие файлы получаются

Все перечисленные результаты находятся в отдельной папке запуска внутри `verification_results`.

| Файл | Содержимое |
| --- | --- |
| `modbus.pml`, `properties.pml`, `config.json` | Копии входных файлов. |
| `pan.c` и другие `pan.*` | Код, сгенерированный SPIN. |
| `pan_safety.exe`, `pan_ltl.exe` | Собранные программы проверки. |
| `spin_version.log`, `gcc_version.log` | Версии инструментов. |
| `generate.log` | Вывод генерации C-кода. |
| `compile_safety.log`, `compile_ltl.log` | Вывод компиляции, включая предупреждения и ошибки. |
| `structure.log` | Подробный результат встроенной проверки конечных состояний. |
| `p01_crc_ignored.log` и остальные логи свойств | Подробности каждой отдельной проверки. |
| `<имя>.trail`, `<имя>_trace.log` | Найденный контрпример и его разбор, если обнаружено нарушение и разбор удался. |
| `report.txt` | Общий отчёт; при сбое подготовки — сообщение об этом сбое. |

При ранней ошибке сборки часть файлов ещё не будет создана. Начните чтение с `report.txt`, затем откройте указанный лог. Папка `verification_results` исключена из Git через `.gitignore`.

## 12. Пример завершённого запуска

После рефакторинга был выполнен запуск `verification_results/run_d96kiwls/`. В нём проверены 13 LTL-свойств и структура обмена:

```text
ИТОГ: всего 14; PASS=14, FAIL=0, ERROR=0.
```

Количество проверок определяется содержимым `properties.pml`: одна проверка `structure` плюс по одной на каждое найденное объявление LTL. Нумерация внутри имён не обязана быть непрерывной: например, после удаления p13 оставшееся имя `p14_completion_clean` продолжает работать.

Чтобы добавить проверку, достаточно добавить именованную формулу в `properties.pml` в показанном формате и снова запустить `python run.py`. Скрипт найдёт новое имя, передаст его верификатору через `-N` и добавит результат в общий отчёт.
