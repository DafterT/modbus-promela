Модель обмена Modbus на языке **Promela** и проверка её свойств в **SPIN**. Один Master отправляет запросы трём Slave. Модель описывает адресную и широковещательную запись регистра, обработку ошибок запроса и обращение к отсутствующему устройству.

Скрипт собирает верификаторы, выполняет структурную проверку и проверяет 14 LTL-свойств. При нарушении свойства сохраняет контрпример и его пошаговый разбор.

## Запуск

### Требования

- **Python 3.9+** со стандартной библиотекой.
- **SPIN 6**. См. [установку SPIN](https://spinroot.com/spin/Man/README.html).
- **GCC** для компиляции верификаторов. В Windows можно использовать [GCC из MSYS2 UCRT64](https://www.mingw-w64.org/getting-started/msys2/).

### Настройка и первый запуск

```sh
git clone https://github.com/DafterT/modbus-promela.git
cd modbus-promela
```

Укажите пути к SPIN и GCC в [config.json](config.json). В репозитории задана конфигурация для Windows:

```json
{
  "spin": "%LOCALAPPDATA%/Programs/Spin/spin.exe",
  "cc": "C:/msys64/ucrt64/bin/gcc.exe"
}
```

Если инструменты доступны в `PATH`, укажите `"spin": "spin"` и `"cc": "gcc"`. В путях Windows используйте `/` или экранируйте обратные слеши: `\\`.

Запустите все проверки из корня проекта:

```sh
python run.py
```

Результаты выводятся в консоль и сохраняются в `verification_results/run_*/report.txt`. Для каждого запуска создаётся отдельная папка с логами проверок.

## Модель и свойства

У каждого Slave есть два регистра с адресами `0` и `1`. Изначально они равны нулю, записанные значения сохраняются между транзакциями. Master выбирает параметры запроса независимо друг от друга:

| Параметр | Значения |
| --- | --- |
| Получатель | `0` для всех Slave, `1`–`3` для конкретного устройства, `4` для отсутствующего устройства. |
| Адрес регистра | `0` или `1` для записи, `2` для проверки ошибки. |
| Значение | `1` или `2`. |
| Функция | `0x06` для записи, `0x03` как неподдерживаемая в модели функция. |
| CRC | Логический признак корректности `crc_ok`. |

Всего получается 120 сочетаний параметров, включая запросы с несколькими ошибками одновременно.

Slave обрабатывает запрос, если указан его адрес или адрес `0`. Сначала проверяет CRC, затем функцию и адрес регистра. Неверная CRC приводит к игнорированию кадра. При верной CRC неподдерживаемая функция даёт исключение `1`, а функция `0x06` с адресом регистра `2` даёт исключение `2`. Проверки прекращаются на первой найденной ошибке.

При корректном адресном запросе выбранный Slave записывает регистр и возвращает его адрес и значение. Широковещательный запрос обрабатывают все три Slave без ответа, в том числе при ошибках. На запрос к адресу `4` никто не отвечает.

Master выполняет одну транзакцию за раз и ожидает завершения обработки всеми Slave. Если на адресный запрос нет ответа, фиксирует тайм-аут.

| Свойство | Что проверяется |
| --- | --- |
| `p01_crc_ignored` | Неверная CRC не приводит к записи или ответу. |
| `p02_absent_slave` | Отсутствующий адрес приводит к тайм-ауту без изменения памяти. |
| `p03_broadcast_silent` | На широковещательный запрос никто не отвечает. |
| `p04_broadcast_written` | Корректную широковещательную запись выполняют все Slave. |
| `p05_addressed_write` | Корректная адресная запись выполняется и завершается нормальным ответом. |
| `p06_write_isolation` | Адресный запрос не меняет невыбранный регистр получателя и память остальных устройств. |
| `p07_normal_response` | Нормальный ответ соответствует корректному запросу. |
| `p08_illegal_function` | Адресный запрос с верной CRC и неподдерживаемой функцией даёт исключение `1` без записи. |
| `p09_illegal_register` | Адресный запрос с верной CRC, функцией `0x06` и несуществующим регистром даёт исключение `2` без записи. |
| `p10_write_authorized` | Каждая запись допустима по содержимому и адресу запроса. |
| `p11_single_response` | За транзакцию отправляется не более одного ответа. |
| `p12_transaction_progress` | Начатая транзакция обязательно достигает результата. |
| `p13_completion_clean` | При завершении все Slave обработали запрос и каналы пусты. |
| `p14_invalid_broadcast` | Ошибочный широковещательный запрос не меняет память и не создаёт ответа. |

Формулы записаны в [properties.pml](properties.pml). Скрипт читает имена свойств из объявлений `ltl` и запускает каждую проверку отдельно.

## Результаты

| Статус | Значение |
| --- | --- |
| `PASS` | Поиск завершён без нарушений. |
| `FAIL` | Найдено нарушение; сохранён контрпример и его воспроизведение. |
| `ERROR` | Ошибка запуска, компиляции или незавершённый поиск. |

Структурная проверка `structure` ищет недопустимые конечные состояния, например остановку Master в ожидании сообщения, которое никто не может отправить. Остальные проверки относятся к LTL-свойствам.

В [сохранённом прогоне](report/verification/README.md) со SPIN 6.5.1 и GCC 16.2.0 все 15 проверок завершились успешно: `PASS=15, FAIL=0, ERROR=0`. Суммарное время поиска составило 8 минут 29 секунд без учёта генерации и компиляции верификаторов, расход памяти достигал около 3,3 Гбайт.

### Если проверка не прошла

- При `FAIL` откройте лог проверки и файл `<имя_проверки>_trace.log` с разбором контрпримера.
- При `ERROR` проверьте пути в [config.json](config.json) и лог указанного этапа. Лимит одной команды составляет 180 секунд, глубина поиска ограничена 1 000 000 шагов.
