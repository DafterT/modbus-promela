# Модель Modbus RTU на Promela: объяснение для начинающего

Полный исходный код находится в файле [modbus.pml](modbus.pml). Этот документ объясняет его переменные, процессы, каналы и последовательность действий.

Модель описывает обмен между одним Master и тремя Slave по общей шине RS-485. Master посылает запросы, а Slave обрабатывают их. Каждый Slave имеет два holding-регистра: регистр с адресом 0 и регистр с адресом 1.

Реализована запись одного регистра — функция FC06. Функция FC03 используется только для получения ответа о неподдерживаемой функции. Поведение устройств находится в `modbus.pml`, а 14 LTL-свойств — в [properties.pml](properties.pml), который подключает модель. В самом `modbus.pml` нет LTL-формул, `assert` и `never claims`.

Проверка свойств запускается командой `python verify.py`. Подробное объяснение свойств, добавленных наблюдательных переменных и Python-скрипта находится в [readme_2.md](readme_2.md).

## 1. Что здесь означает «модель»

Promela — язык описания взаимодействующих процессов. SPIN исполняет такую модель и может исследовать возможные порядки выполнения её действий.

В этой работе процесс изображает устройство, канал — доставку сообщения, а переменная — часть состояния устройства или обмена.

Программа не подключается к настоящей RS-485. Она позволяет проследить, какой запрос отправлен, кто его обработал, что записалось в регистры и какой результат получил Master.

Выбраны следующие упрощения:

- Передаются целые сообщения; отдельные биты UART и электрические сигналы RS-485 не описаны.
- Проверка CRC заменена логическим признаком `crc_ok`. Значение `true` означает правильную CRC, `false` — ошибку.
- Значение для записи выбирается из чисел 1 и 2. Начальное значение всех регистров — 0.
- Адреса регистров и их значения представлены типом `byte`. В настоящем Modbus это 16-битные поля; небольшой диапазон здесь сокращает число состояний.
- Выполняются три последовательные транзакции. Количество задаёт `TRANSACTION_COUNT`.
- Реальные интервалы RTU и таймеры заменены ожиданием завершения обработки запроса.
- Ответы не повреждаются, сообщения не теряются при доставке. Ошибка CRC явно выбирается только для запроса.
- Повторных передач, арбитража и других функций Modbus нет.

## 2. Как проходит одна транзакция

Транзакция — один запрос Master вместе с его обработкой и получением результата.

1. Master выбирает адрес Slave, адрес регистра и значение.
2. Master выбирает один из шести типов запроса.
3. Одинаковая копия запроса помещается в канал каждого Slave.
4. Все три Slave получают свои копии. Порядок их работы может меняться.
5. Каждый Slave проверяет, относится ли запрос к нему, и при необходимости выполняет дальнейшие проверки и запись.
6. Каждый Slave отправляет служебное уведомление о завершении обработки.
7. После трёх уведомлений Master получает ответ, фиксирует отсутствие ответа либо завершает broadcast.
8. Master печатает содержимое регистров. Затем может начаться следующая транзакция.

Запросы не перекрываются: Master не начинает следующий обмен, пока не закончена обработка предыдущего.

## 3. Основные конструкции Promela

| Запись в коде | Простое объяснение |
| --- | --- |
| `/* ... */` | Комментарий. Поясняет код и не выполняется. |
| `#define FC06 6` | Задаёт имя для постоянного значения. Перед разбором модели `FC06` заменяется на `6`. |
| `byte` | Целое число от 0 до 255. |
| `bool` | Логическое значение: `false` или `true`, то есть 0 или 1. |
| `mtype` | Тип для именованных значений, например состояний Master. |
| `byte holding_register_0[4]` | Массив из четырёх чисел. Индексы массива: 0, 1, 2, 3. |
| `chan` | Канал, через который процессы передают сообщения. |
| `proctype` | Описание поведения процесса. Само описание ещё не запускает процесс. |
| `run Slave(1)` | Запускает новый процесс `Slave` с параметром 1. |
| `init` | Начальный процесс, который создаёт устройства модели. |
| `if ... fi` | Выбирает одну доступную ветвь. `fi` завершает этот блок. |
| `do ... od` | Повторяет выбор доступных ветвей. `od` завершает описание цикла. |
| `::` | Начинает очередную ветвь внутри `if` или `do`. |
| `условие -> действия` | Действия можно начать, когда условие истинно. |
| `else` | Доступно, когда в этом же `if` или `do` нет другой доступной ветви. |
| `skip` | Разрешённое действие, которое ничего не меняет. |
| `break` | Выход из ближайшего цикла `do`. |
| `atomic { ... }` | Объединяет действия в один логический шаг без переключения на другой процесс, пока действия не блокируются. |
| `канал!значения` | Отправка сообщения в канал. Может ждать, если буфер заполнен. |
| `канал?переменные` | Получение сообщения и запись его полей в переменные. Ждёт, если подходящего сообщения нет. |
| `slave_done?true` | Получение сообщения с конкретным значением `true`. Это не присваивание переменной. |
| `len(канал)` | Число сообщений, которые сейчас находятся в буфере канала. |
| `printf(...)` | Вывод поясняющей строки при симуляции. `%d` заменяется десятичным числом, `\n` означает новую строку. |
| `transaction_number++` | Увеличивает номер транзакции на 1. |
| `==`, `!=`, `<`, `>` | Равно, не равно, меньше, больше. |
| `||` | Логическое «или». Достаточно истинности одного из двух условий. |
| `=` | Присваивание значения. Отличается от сравнения `==`. |

Важное отличие от привычного `if` в других языках: если несколько ветвей доступны одновременно, Promela может выбрать любую из них. При обычной симуляции SPIN выбирает конкретный путь. При полном поиске он исследует альтернативы с учётом своих сокращений пространства состояний.

Например, в блоке выбора адреса все три присваивания доступны. Поэтому код не обязан сначала выбирать 1, затем 2, затем 3.

## 4. Константы

| Имя | Значение | Назначение |
| --- | --- | --- |
| `TRANSACTION_COUNT` | 3 | Количество транзакций за одно выполнение модели. |
| `FC06` | 6 | Код функции Write Single Register: запись одного holding-регистра. |
| `FC03` | 3 | Код функции Read Holding Registers, которую Slave намеренно не поддерживают. |

В комментариях встречаются обозначения `0x06`, `0x03`, `0x80`. Префикс `0x` означает шестнадцатеричную запись. Соответствующие десятичные числа — 6, 3 и 128. В исполняемых выражениях модели используются десятичные числа и константы `FC06`, `FC03`.

## 5. Все глобальные переменные

Глобальные переменные объявлены до процессов. Они описывают состояние всей модели и доступны для наблюдения. Переменные без явного начального значения изначально равны 0; для `bool` это `false`.

### 5.1. Состояние Master и номер транзакции

| Переменная | Тип | Назначение |
| --- | --- | --- |
| `master_state` | `mtype` | Показывает этап работы Master или результат последнего завершённого обмена. Изначально `MASTER_PREPARING`. |
| `transaction_number` | `byte` | Номер текущей транзакции. Изначально 0, перед первым запросом становится 1. |

Значения `master_state`:

| Значение | Что означает |
| --- | --- |
| `MASTER_PREPARING` | Master подготавливает новый запрос и очищает сведения о предыдущем обмене. |
| `MASTER_WAITING` | Запрос доставлен, Master ожидает завершения обработки Slave. |
| `MASTER_RESPONSE` | Master принял ответ. Нормальный это ответ или исключение, показывает `response_exception_code`. |
| `MASTER_TIMEOUT` | Для адресного запроса обработка завершена, а ответа нет. |
| `MASTER_BROADCAST_DONE` | Все Slave закончили обработку broadcast; ответ не ожидается. |

После третьей транзакции Master заканчивает выполнение, сохраняя последнее значение `master_state`. Отдельного состояния остановки в модели нет.

### 5.2. Текущий запрос Master

| Переменная | Тип | Назначение и возможные значения |
| --- | --- | --- |
| `slave_address` | `byte` | Адрес получателя: 1–3 — существующие Slave, 4 — отсутствующий Slave, 0 — broadcast. |
| `function_code` | `byte` | Функция запроса: `FC06` для записи или `FC03` для проверки неподдерживаемой функции. |
| `register_address` | `byte` | Адрес регистра: 0 или 1 для существующего регистра, 2 для ошибочного запроса. |
| `register_value` | `byte` | Значение, которое Master предлагает записать: 1 или 2. |
| `crc_ok` | `bool` | Признак корректности CRC запроса. |

Во время обработки одной транзакции эти поля не меняются. Новые значения выбираются только перед следующим запросом.

Для FC03 общий формат сообщения сохраняется ради простоты модели. Поле `register_value` при этом не используется: Slave отвергает неподдерживаемый код функции до обработки остальных данных. Полная структура настоящего запроса FC03 здесь не моделируется.

### 5.3. Регистры и признаки записи

| Переменная | Тип | Назначение |
| --- | --- | --- |
| `holding_register_0[4]` | Массив `byte` | `holding_register_0[slave_id]` хранит регистр с адресом 0 у указанного Slave. |
| `holding_register_1[4]` | Массив `byte` | `holding_register_1[slave_id]` хранит регистр с адресом 1 у указанного Slave. |
| `slave_write_performed[4]` | Массив `bool` | `slave_write_performed[slave_id]` показывает, выполнил ли этот Slave запись в текущей транзакции. |

Примеры: `holding_register_0[2]` — регистр 0 у Slave 2; `holding_register_1[3]` — регистр 1 у Slave 3.

Нулевые элементы этих массивов не используются. Четыре элемента нужны, чтобы индексы 1, 2, 3 прямо совпадали с адресами Slave. Broadcast не имеет собственных регистров: адрес 0 обозначает обращение ко всем трём устройствам.

Перед каждым запросом Master сбрасывает признаки записи в `false`. Сами регистры сохраняют значения между транзакциями. Если в регистр повторно записано то же число, признак всё равно становится `true`: операция записи состоялась, даже если число не изменилось.

Для формальной проверки добавлены ещё четыре наблюдательные переменные:

| Переменная | Тип | Назначение |
| --- | --- | --- |
| `previous_register_0[4]` | Массив `byte` | Снимок регистра 0 каждого Slave перед текущим запросом. Позволяет проверить, какие значения сохранились после обмена. |
| `previous_register_1[4]` | Массив `byte` | Такой же снимок регистра 1. |
| `slave_processed[4]` | Массив `bool` | Признак завершения обработки текущего запроса каждым Slave, включая игнорирование запроса. |
| `responses_sent` | `byte` | Общее число отправленных ответов в текущей транзакции: нормальных и с исключением. Служебные уведомления в `slave_done` сюда не входят. |

В трёх массивах из этой таблицы индекс 0 также не используется. Master обнуляет `slave_processed[1..3]` и `responses_sent` перед новым запросом, затем копирует шесть значений регистров в `previous_register_0` и `previous_register_1`. Slave отмечает завершение обработки и увеличивает счётчик при отправке ответа.

Эти данные читают свойства, а не условия работы устройств. Они не выбирают сценарий, не разрешают запись, не заменяют сообщения `slave_done` и не меняют правила Modbus. Например, ждать завершения Master продолжает по трём сообщениям канала, а не по массиву `slave_processed`.

### 5.4. Принятый ответ

| Переменная | Тип | Назначение |
| --- | --- | --- |
| `response_slave_address` | `byte` | Адрес Slave, от которого принят ответ. |
| `response_function_code` | `byte` | Код функции в ответе: 6 для успешной записи, 131 или 134 для исключения. |
| `response_register_address` | `byte` | Адрес записанного регистра в нормальном ответе. В исключении используется условное значение 0. |
| `response_register_value` | `byte` | Записанное значение в нормальном ответе. В исключении используется условное значение 0. |
| `response_exception_code` | `byte` | 0 — нормальный ответ; 1 — неподдерживаемая функция; 2 — недопустимый адрес регистра. |

До нового запроса эти поля очищаются. Они описывают принятый ответ, когда `master_state == MASTER_RESPONSE`. Сам по себе `response_exception_code == 0` ещё не означает успешный обмен: ноль также находится в поле после очистки, при broadcast и при отсутствии ответа.

В настоящем ответе с исключением нет полей адреса регистра и его значения. В модели они заполнены нулями, чтобы все ответы помещались в один простой канал с одинаковым набором полей.

## 6. Все каналы и представление общей шины

### 6.1. `slave_requests`: доставка запросов

```promela
chan slave_requests[3] = [1] of { byte, byte, byte, byte, bool };
```

Первые квадратные скобки, `[3]`, означают массив из трёх отдельных каналов. Вторые, `[1]`, задают вместимость каждого канала: одно сообщение.

Одно сообщение содержит пять полей в строго определённом порядке:

```text
адрес Slave, код функции, адрес регистра, значение, корректность CRC
```

| Устройство | `slave_id` | Канал запросов | Индекс в массивах регистров |
| --- | --- | --- | --- |
| Slave 1 | 1 | `slave_requests[0]` | 1 |
| Slave 2 | 2 | `slave_requests[1]` | 2 |
| Slave 3 | 3 | `slave_requests[2]` | 3 |

Поэтому при получении используется индекс `slave_id - 1`.

Все Slave получают одну и ту же информацию об общем кадре. Адрес внутри сообщения определяет, кто должен выполнить запрос. При обычном адресе два остальных Slave просто игнорируют свои копии.

Если бы все Slave читали один общий обычный канал, сообщение забрал бы только один из них. Остальные его не увидели бы, и broadcast работал бы неправильно. Три канала доставки позволяют явно представить получение общего кадра всеми устройствами.

### 6.2. `slave_responses`: ответы Slave

```promela
chan slave_responses = [1] of { byte, byte, byte, byte, byte };
```

Это один общий канал вместимостью одно сообщение. Порядок полей:

```text
адрес Slave, код функции ответа, адрес регистра, значение, код исключения
```

Буфера из одного сообщения достаточно: адреса Slave уникальны, на адресный запрос отвечает одно устройство, а на broadcast ответа нет.

Буфер важен и для синхронизации. Slave может сначала поместить ответ в канал, затем сообщить о завершении. Если бы канал ответов был без буфера, Slave ждал бы получения ответа Master, а Master в это время ждал бы уведомления Slave.

### 6.3. `slave_done`: уведомления о завершении

```promela
chan slave_done = [3] of { bool };
```

Канал вмещает три уведомления. Каждый Slave отправляет одно значение `true` после обработки очередного запроса. Уведомление отправляется и при игнорировании чужого адреса или неправильной CRC.

Это служебный механизм синхронизации модели. По настоящей шине Modbus такие уведомления не передаются. Поэтому уведомление после broadcast не является ответом на broadcast.

В уведомлении нет адреса Slave: Master важно получить три завершения. Каждое устройство отправляет ровно одно уведомление на свою копию запроса. Второго уведомления от того же Slave до следующего запроса быть не может, а следующий запрос Master отправляет только после трёх завершений.

## 7. Процесс `Master()` по блокам

`proctype Master()` описывает поведение одного Master. Параметров и локальных переменных у него нет; он использует глобальные поля запроса, ответа и состояния.

### 7.1. Цикл транзакций

В начале `do` проверяется `transaction_number < TRANSACTION_COUNT`. Если условие истинно, начинается очередной обмен. Master переходит в `MASTER_PREPARING` и увеличивает номер транзакции.

Вторая ветвь цикла, `else -> break`, становится доступна после достижения установленного количества транзакций. Master выходит из цикла и заканчивает работу.

### 7.2. Очистка сведений о предыдущем обмене

Пять полей `response_...` обнуляются, а три признака `slave_write_performed` становятся `false`. Это позволяет отличать результаты текущего запроса от предыдущего.

Одновременно сбрасываются три признака `slave_processed` и счётчик `responses_sent`. После этого шесть присваиваний сохраняют текущие регистры в массивы `previous_register_0` и `previous_register_1`. Регистры при этом только читаются. Например, `previous_register_1[2] = holding_register_1[2]` запоминает значение регистра 1 у Slave 2 до нового запроса.

Очистка выполняется после перехода в `MASTER_PREPARING`. В этом состоянии ответ ещё не считается принятым, а новые поля запроса ещё могут быть не полностью подготовлены.

### 7.3. Выбор исходных параметров

Три блока `if` независимо выбирают:

- адрес Slave из 1, 2, 3;
- адрес регистра из 0, 1;
- значение из 1, 2.

Далее устанавливаются `function_code = FC06` и `crc_ok = true`. На этом месте подготовлен корректный адресный запрос записи.

### 7.4. Выбор одного из шести сценариев

Следующий `if` либо оставляет запрос корректным, либо меняет один его параметр.

| Ветка | Что меняется | Результат обработки |
| --- | --- | --- |
| `skip` | Ничего | Выбранный Slave записывает регистр и отвечает нормально. |
| `crc_ok = false` | CRC становится неправильной | Запись и ответ отсутствуют; Master фиксирует тайм-аут. |
| `slave_address = 4` | Получатель отсутствует | Все три Slave игнорируют запрос; Master фиксирует тайм-аут. |
| `register_address = 2` | Указан отсутствующий регистр | Выбранный Slave возвращает исключение 2. |
| `function_code = FC03` | Указана неподдерживаемая функция | Выбранный Slave возвращает исключение 1. |
| `slave_address = 0` | Запрос становится broadcast | Все три Slave записывают регистр, ответов нет. |

Выбирается ровно одна ветвь. Например, сценарий с неправильной CRC здесь не совмещается с broadcast или отсутствующим Slave.

На каждой транзакции доступны все шесть вариантов, в том числе повтор уже выбранного. Одно выполнение из трёх транзакций не обязано показать все сценарии и даже может трижды повторить один из них.

### 7.5. Вывод запроса

Первый `printf` печатает номер транзакции и все пять полей запроса. Это позволяет понять выбранный сценарий без просмотра внутренних шагов SPIN.

### 7.6. Доставка кадра

В блоке `atomic` Master устанавливает `MASTER_WAITING` и отправляет одинаковые сообщения в три канала `slave_requests`.

Так один общий кадр становится доступен всем Slave за один логический шаг. Slave начинают разбирать копии после этого блока. Их дальнейшая обработка не объединена в один общий `atomic`.

К началу доставки все три канала пусты: предыдущие запросы уже получены и обработаны. Поэтому отправки помещаются в буферы и не блокируют этот блок.

### 7.7. Ожидание завершения обработки

Три строки `slave_done?true` получают три служебных уведомления. Если следующего уведомления пока нет, Master ждёт, а Slave могут продолжать работу.

После третьего получения известно, что ни один Slave уже не выполняет запись и не собирается отправлять ответ на этот запрос.

### 7.8. Завершение broadcast

Если `slave_address == 0`, Master переходит в `MASTER_BROADCAST_DONE`. Получение из канала ответов не выполняется. К этому моменту все три Slave уже закончили обработку.

Так представлено необходимое ожидание обработки broadcast перед новым запросом. В настоящем обмене ему соответствует пауза Master, называемая turnaround delay.

### 7.9. Получение адресного ответа или тайм-аут

Для адресного запроса Master проверяет `len(slave_responses) > 0`.

Если сообщение есть, оно извлекается в пять глобальных переменных `response_...`. Состояние меняется на `MASTER_RESPONSE`, затем ответ выводится в консоль.

Если сообщения нет, выполняется ветвь `else`: состояние становится `MASTER_TIMEOUT` и печатается сообщение об отсутствии ответа.

Этот тайм-аут означает отсутствие ответа после завершения всех обработчиков. Модель предполагает, что ожидание достаточно для обработки запроса; слишком короткий таймер и поздние ответы не рассматриваются. Пустота канала сразу после отправки запроса ещё не позволяла бы сделать такой вывод.

После трёх уведомлений содержимое канала ответов уже не может измениться само: новый ответ на текущий запрос не появится, а читать канал может только Master. Поэтому проверка длины и последующее получение согласованы.

### 7.10. Вывод регистров

Последний `printf` показывает пары `(регистр 0, регистр 1)` для каждого Slave. Например, `Slave 2=(1,2)` означает, что у Slave 2 регистр 0 равен 1, а регистр 1 равен 2.

Этот вывод выполняется после завершения обработки, поэтому показывает итог всей транзакции, включая все записи broadcast.

## 8. Процесс `Slave(byte slave_id)` и все его переменные

Это одно описание поведения, по которому запускаются три отдельных процесса. У каждого процесса собственные локальные переменные.

| Имя | Тип | Назначение |
| --- | --- | --- |
| `slave_id` | Параметр `byte` | Собственный неизменный адрес устройства: 1, 2 или 3. Задаётся при запуске процесса. |
| `request_slave_address` | `byte` | Адрес получателя в принятом запросе. Может отличаться от собственного адреса устройства. |
| `request_function_code` | `byte` | Код функции в локальной копии запроса. |
| `request_register_address` | `byte` | Адрес регистра в локальной копии запроса. |
| `request_register_value` | `byte` | Предлагаемое значение для записи. |
| `request_crc_ok` | `bool` | Признак корректности CRC принятой копии. |
| `exception_code` | `byte` | Локальный результат проверок: 0, 1 или 2. Обнуляется при получении каждого запроса. |

Например, у Slave 2 параметр `slave_id` всегда равен 2. Если он получил копию запроса для Slave 1, его `request_slave_address` будет равен 1. Сравнение этих значений позволяет проигнорировать чужой запрос.

### 8.1. Метка `end_slave_wait` и цикл ожидания

Метка стоит перед `do`, где Slave ждёт сообщения. Префикс `end` имеет специальное значение для SPIN: эту точку можно считать допустимым конечным состоянием процесса.

После трёх транзакций Master завершает работу, а Slave остаются готовы принимать новые сообщения. Новых сообщений уже нет, и такое ожидание является нормальным завершением рассматриваемого обмена. Метка не завершает процесс и не меняет его алгоритм.

Сам цикл Slave бесконечный: ветки с `break` у него нет. Это изображает устройство, которое постоянно готово к следующему запросу.

### 8.2. Получение своей копии

Оператор получения читает канал `slave_requests[slave_id - 1]`. Пять полей сообщения записываются в пять локальных переменных `request_...` в том же порядке, в котором их отправил Master.

Пока сообщение не пришло, эта операция ждёт. После получения `exception_code` сбрасывается в 0.

### 8.3. Проверка адреса

Условие `request_slave_address == slave_id || request_slave_address == 0` означает: запрос адресован этому Slave либо всем Slave.

Если условие ложно, срабатывает внешний `else -> skip`. Slave не меняет регистры и не отправляет ответ, но затем всё равно сообщает о завершении обработки своей копии.

### 8.4. Проверка CRC

Если адрес подходит, проверяется `request_crc_ok`. При `false` Slave печатает `ignored (bad CRC)` и не выполняет внутренние блоки проверки функции, записи и ответа.

Следовательно, неправильная CRC не превращается в ответ с исключением: сообщение игнорируется.

### 8.5. Проверка функции

При правильной CRC проверяется `request_function_code != FC06`. Если функция отличается от поддерживаемой, `exception_code` становится 1.

Проверка регистра и запись находятся в ветви `else`, поэтому при неподдерживаемой функции они не выполняются. Для FC03 результатом будет ответ с исключением 1.

### 8.6. Проверка адреса регистра

Для FC06 проверяется `request_register_address > 1`. Значения 0 и 1 допустимы, значение 2 вызывает исключение 2.

Отрицательный адрес здесь невозможен: поле имеет тип `byte`. При ошибочном адресе код записи не выполняется.

### 8.7. Запись регистра

В небольшом блоке `atomic` выбирается нужный массив: при адресе 0 — `holding_register_0`, иначе — `holding_register_1`. В элемент с индексом `slave_id` записывается `request_register_value`.

В том же логическом шаге `slave_write_performed[slave_id]` становится `true`. Это позволяет видеть изменение регистра и признак выполненной записи согласованно.

Далее `printf` сообщает адрес Slave, адрес регистра и записанное значение. Код записи одинаков для адресного запроса и broadcast: оба случая уже прошли проверку адреса.

### 8.8. Подготовка и отправка ответа

После проверки функции и регистра рассматривается адрес запроса.

Если адрес равен 0, выполняется `skip`: ни нормальный ответ, ни ответ с исключением не отправляется.

Для адресного запроса выбор зависит от `exception_code`:

- При 0 отправляются собственный адрес Slave, исходный код функции, адрес регистра, значение и нулевой код исключения. Это нормальный ответ FC06, повторяющий данные запроса после записи.
- При 1 или 2 к коду функции прибавляется 128 и отправляется код исключения. Поля регистра и значения заполняются нулями, поскольку общий формат канала содержит эти места.

Прибавление 128 устанавливает старший бит кода функции для используемых кодов 3 и 6:

| Запрос | Функция в ответе с исключением | Десятичное число в выводе |
| --- | --- | --- |
| FC03, то есть `0x03` | `0x83` | 131 |
| FC06, то есть `0x06` | `0x86` | 134 |

Для правильной CRC ответ с исключением означает, что запрос получен, но запрошенное действие выполнить нельзя. Записи при таком ответе нет.

В обеих ветвях отправка ответа и `responses_sent++` находятся в небольшом `atomic`. Так помещение сообщения в канал и учёт этого сообщения наблюдаются согласованно. Счётчик увеличивается только после успешной отправки; на broadcast обе ветви отправки пропускаются.

### 8.9. Уведомление о завершении

После всех ветвей обработки выполняется небольшой блок:

```promela
atomic {
    slave_processed[slave_id] = true;
    slave_done!true;
}
```

Первое действие отмечает завершение обработки для проверки свойств. Второе посылает прежнее служебное уведомление Master. Блок выполняется и после записи, и после исключения, и после игнорирования запроса. Вместимость канала завершений равна 3, поэтому три Slave могут поместить свои уведомления без взаимной блокировки.

Если ответ нужен, он помещается в `slave_responses` до уведомления. Если нужна запись, она также уже выполнена. Затем Slave возвращается к ожиданию следующего сообщения.

## 9. Начальный процесс `init`

```promela
init
{
    atomic {
        run Slave(1);
        run Slave(2);
        run Slave(3);
        run Master();
    }
}
```

`init` запускается SPIN автоматически. Он создаёт три Slave с разными адресами и один Master.

`atomic` объединяет создание устройств в начальный шаг: ни одно из них не начинает обмен до создания остальных.

`Master` и `Slave` являются процессами, а не обычными функциями с возвратом результата. `run` создаёт независимо исполняющийся процесс; он не ждёт завершения этого процесса, как вызов обычной функции.

Отдельных пользовательских функций и вспомогательных процессов в файле нет. `printf` и `len` — встроенные операции Promela. Сам `init` служит только для запуска; устройства системы — Master и три Slave.

## 10. Почему ожидания согласованы

Каналы имеют небольшой, но достаточный размер. Каждый канал запросов содержит максимум одну копию, общий канал ответов — максимум один ответ, канал завершений — максимум три уведомления.

Master отправляет запрос всем Slave, прежде чем ожидать уведомления. Каждый Slave может положить ответ в буфер, затем положить уведомление в другой буфер. Поэтому Master не обязан сначала принимать ответ, чтобы Slave смог закончить обработку.

Три уведомления отделяют соседние транзакции. После них текущие запросы уже извлечены из каналов, а адресный ответ, если он был, можно получить до следующего запроса. Накопления запросов от разных транзакций нет.

В модели используются небольшие `atomic` для создания устройств, доставки одного кадра всем Slave, записи регистра вместе с признаком записи, отправки ответа вместе с увеличением счётчика и уведомления о завершении вместе с признаком `slave_processed`. Последние два блока обеспечивают согласованность наблюдательных данных. Полная обработка запроса каждым Slave и вся работа системы целиком не сделаны атомарными.

### 11.4. Как читать вывод

Например, две строки нормального обмена:

```text
Master: transaction=2 slave=1 FC=6 register=0 value=1 CRC=1
Master: response slave=1 FC=6 register=0 value=1 exception=0
```

Master попросил Slave 1 записать 1 в регистр 0. Ответ повторяет эти данные, а `exception=0` указывает на успешную запись.

Строка `Slave 1: ignored (bad CRC)` означает игнорирование ошибочного кадра. Следующая строка `Master: timeout (no response)` сообщает результат адресной транзакции.

При broadcast появятся три строки записи и строка `Master: broadcast completed, no response expected`. Например, итог `Slave 1=(2,0) Slave 2=(2,0) Slave 3=(2,0)` показывает значение 2 в регистре 0 каждого Slave.

Числа 131 и 134 в поле `FC` означают функции ответов с исключением `0x83` и `0x86`. Конкретную причину показывает поле `exception`: 1 или 2.

После последней транзакции SPIN может напечатать отдельное слово `timeout` и показать Slave в `<valid end state>`. Это сообщение самого симулятора: все оставшиеся процессы ждут новые сообщения, а Master уже закончил работу. Оно отличается от строки `Master: timeout (no response)`, которая относится к конкретному запросу.

### 11.5. Генерация и запуск проверяющей программы

Выполняйте следующие команды по очереди. К следующей переходите после успешного завершения предыдущей:

```powershell
& $spinPath -a .\modbus.pml
& $ccPath -O2 -DSAFETY -DNOCLAIM -DCOLLAPSE -o pan.exe pan.c
.\pan.exe -m10000 -w22 -q -b
```

Назначение команд и параметров:

- `spin -a` разбирает модель и создаёт исходный код проверяющей программы: `pan.c` и вспомогательные файлы `pan.*`.
- GCC компилирует этот C-код в `pan.exe`. Сам файл `.pml` GCC не компилирует.
- `-O2` включает оптимизацию C-кода.
- `-DSAFETY` выбирает режим без поиска циклов, `-DNOCLAIM` отключает использование never claim.
- `-DCOLLAPSE` включает сжатие сохраняемых состояний без потери информации.
- `-m10000` задаёт предел глубины поиска 10000 шагов.
- `-w22` задаёт размер хеш-таблицы для хранения состояний.
- `-q` требует пустоты каналов в допустимых конечных состояниях.
- `-b` делает достижение ограничения глубины ошибкой, чтобы незавершённый поиск не принять за успешный.

Эти команды исследуют завершение взаимодействия процессов и состояние каналов. Они не добавляют проверяемые выражения в исходную модель.

Созданные `pan.*` и `pan.exe` — вспомогательные результаты проверки. Для редактирования модели нужен `modbus.pml`; для чтения объяснений — этот README.

GCC 16.2.0 выдал предупреждения `-Wpointer-to-int-cast` и `-Wstringop-overflow` в автоматически сгенерированных файлах `pan.c`/`pan.b`. Компиляция завершилась успешно, `pan.exe` был создан и выполнил поиск. Синтаксических ошибок в итоговом `modbus.pml` SPIN не обнаружил.

Результат `errors: 0` из этой таблицы относится к отдельной проверке структуры взаимодействия. Для содержимого регистров, ответов, исключений и продвижения Master добавлены 14 самостоятельных LTL-проверок. Их формулы, способ запуска, результаты и границы выводов описаны в [readme_2.md](readme_2.md). Число состояний выросло по сравнению с первоначальной моделью, поскольку проверка теперь различает снимки регистров и дополнительные признаки обработки.
